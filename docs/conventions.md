# Conventions (set by ticket 01)

## Stack
- npm workspaces, TypeScript (ESM, NodeNext, strict), vitest, Fastify 5, better-sqlite3, React 18 + Vite.
- Root: `npm test` (vitest run, all packages), `npm run build` (all workspaces, in order shared, server, agent, web).
- Imports between packages use `.js` suffixes inside a package (NodeNext). Tests resolve `@redline/shared` and `@redline/server/test-harness` to source through aliases in root `vitest.config.ts` (no build needed to test).

## Packages (`packages/`)
- `shared` (`@redline/shared`): protocol/API types and `PROTOCOL_VERSION`. Add new request/response types here.
- `server` (`@redline/server`): `src/store.ts` (SQLite + blobs in `<dataDir>/redline.db` and `<dataDir>/blobs/<sha256>`), `src/app.ts` (`buildMainApp` = API + web UI; `buildArtboardApp` = artboards only), `src/start.ts` (`startServer`), `src/main.ts` (env: `REDLINE_DATA_DIR`, `REDLINE_HOST`, `REDLINE_PORT` 3000, `REDLINE_ARTBOARD_PORT` 3001, `REDLINE_ARTBOARD_ORIGIN`, `REDLINE_WEB_DIR`).
- `agent` (`redline-cli`, bin `redline`): `src/cli.ts` (`login`, `init`, `agent`, `mcp`).
- `web`: `src/App.tsx`, built to `packages/web/dist`, served by the server at `/` (SPA fallback). `npm run dev -w @redline/web` proxies `/api` to localhost:3000.

## Seam-1 test harness
```ts
import { startTestServer } from "@redline/server/test-harness";
const server = await startTestServer();   // real server, temp data dir, random ports
server.get("/api/..."); server.post("/api/...", body);   // fetch Response, JSON body
server.url; server.artboardOrigin; server.dataDir; server.blobCount();
await server.stop();                       // closes and removes the data dir
```
Extend `TestServer` in `packages/server/src/test-harness.ts` (e.g. `put`, `delete`, a WebSocket agent client) rather than building another harness. `server.restart({ downForMs? })` stops the server and starts a new one on the same data folder AND the same ports (a process restart: queue, agents' links and data survive; agent sockets drop). `url` is a getter.

## Agent protocol (ticket 04)
- Types in `@redline/shared`: `AGENT_ENDPOINT` (`/agent`, WebSocket on the main port), `AgentHello` (first message: token, protocolVersion, machine, folder, kind), `ServerToAgentMessage` (`welcome` / `error`), `AgentToServerMessage`, `AgentCloseCode` (4401 unauthorized, 4426 incompatible protocol, 4400 bad hello), `AGENT_UPDATE_COMMAND`, `AgentInfo`. Add new work-item and event messages to these unions (bump `PROTOCOL_VERSION` on incompatible changes).
- Token: `abt_...`, kept in the `settings` table; `GET /api/agent-token`, `POST /api/agent-token/regenerate` (closes every agent socket with 4401); `GET /api/agents` lists agents (one row per machine+folder, status online/offline).
- Server side lives in `packages/server/src/agents.ts` (`registerAgentRoutes`; keeps a `connected` socket map, the place to add routing of work items to agents). Store: `markAgentOnline/Offline`, `listAgents`.
- Harness: `server.connectAgent({ token?, protocolVersion?, machine?, folder?, kind? })` returns `{ hello, messages, send(msg), closed, close() }`; token defaults to the server's current one. Use `send` + `messages` to test new agent protocol messages.
- Agent package: `login.ts` (`login`, `readLogin`, config in `$REDLINE_CONFIG_DIR` or `~/.config/redline/login.json`), `claude.ts` (`checkClaude`), `connection.ts` (`connectToServer` -> `{ agentId, closed, close }`, uses Node's global WebSocket), `cli.ts` (`redline login`, `redline agent [--global]`). Agent tests import the server harness and call these modules directly.
- Web: `AgentsScreen.tsx`, reached through `#/agents` (hash switch in `main.tsx`; no router yet).

## Patterns
- Tests live in `packages/<pkg>/test/*.test.ts`, named by behavior, driving the HTTP API only (no direct store access). No tests on internal modules (retry policy, router, view helpers...): cover them through the HTTP API, seam 2 or a journey. Kept on purpose because a seam test would be disproportionate: `packages/web/test/canvas-view.test.ts` (pure zoom/pan/fit geometry), `packages/web/test/message-context.test.ts` (which artboards count as visible for a viewport and a zoom: geometry a journey cannot pin), `packages/web/test/element-chips.test.ts` (chip identity across renderings of a responsive artboard, and how a bridge name splits into kind and name), `packages/shared/test/canvas-element-summary.test.ts` (one-line summary of each canvas element kind: truncation and whitespace cases), `canvas-geometry.test.ts` (arrow and frame geometry: numbers worked out by hand, a journey cannot pin them), `note-markdown.test.ts` (the markdown subset: many small input/output cases), `packages/shared/test/reading-order.test.ts` (rows, groups and titles of the reading order: pure geometry with many layouts a journey cannot pin), `packages/web/test/toc-items.test.ts` (grouping, filtering and centred-artboard picking of the table of contents: pure functions over lists and geometry), `packages/web/test/message-links.test.ts` (splitting a message into text, links and addresses: pure parsing with many string cases), `play-frames.test.ts` (the frame/fill/narrow-window matrix of `presentationOf`), `view-settings.test.ts` (the hidden-rendering rules and their edge cases), the arg-building and stream-parsing tests of the Claude Code adapter (recorded fixtures).
- UI copy is French (labels, buttons, placeholders, aria-labels, status texts, mock-up vocabulary: Résoudre, Répondre, Toi, Annuler, Nouvelle page, Nouveau projet, Historique, Restaurer, Projets...). Code, identifiers, logs, commit messages and docs are English. Server error messages (`{ "error": ... }`) stay English.
- Routes: JSON under `/api/...`; create returns 201 with the entity; validate input at the route, errors as `{ "error": "..." }`.
- Artboards are served only by the artboard listener (separate port = separate origin) at `/pages/<pageId>/<path>` with CSP `sandbox allow-scripts`; the web UI embeds them with `<iframe sandbox="allow-scripts">` (never `allow-same-origin`).
- File content is UTF-8 text for now (`files: { path: string }`); a version is a row mapping path to sha256 hash. Page file paths are checked by ONE `isSafePath` (`@redline/shared`: relative, `/` only, no `.`/`..`/empty segment, no `\`, `:` or NUL); the server's `validation.ts` holds the one `manifestError` (manifest AND tweaks.json), `designSystemError`, `versionRequestError` (used by `/api` and `/agent-api`), `requiredString`, `modelChoiceError`/`modelChoiceOf`. Use them in any new route instead of hand-written checks. Schema is created in `Store`'s constructor with `CREATE TABLE IF NOT EXISTS`; add tables/columns there.
- Port 3000 is often taken on this dev machine; use random ports (the harness does) or env overrides.
- Docker: `Dockerfile` + `docker-compose.yml` at repo root (volume `redline-data` at `/data`); the opt-in `npm run test:docker` (REDLINE_DOCKER_TEST=1) builds the image; keep any new server env var documented in README.md.
- Browser journeys: `packages/web/test/*.journey.test.ts` use the `playwright` library inside vitest (headless chromium; run `npx playwright install chromium` once), build the web app to a temp dir with vite and pass it as `startTestServer({ webDir })`. Versions carry `message` and `origin` (`VERSION_ORIGINS` in shared); `POST /api/pages/:id/versions` records one (`store.addVersion` server-side). Origins: `creation` (first version of every page: new page, `create_page`, design system), `thread`, `conversation`, `terminal`, `tweak`, `restore`. A version also carries `originId` / `originLabel` (thread or conversation id and title at the time) when an agent published it, see "Product decisions of 2026-10-22".
- Artboard bridge (ticket 06): artboards are in a sandboxed cross-origin iframe, so the web UI cannot read their DOM. The artboard server injects `<script src="/__redline/bridge.js">` into every served `.html` (`packages/server/src/bridge.ts`, plain ES5 string). The web UI talks to it with `postMessage` (target origin `"*"`, since the iframe origin is opaque) and accepts messages only when `event.source === iframe.contentWindow`; the bridge accepts only `event.source === window.parent`. Messages: parent->artboard `redline:set-mode {picking, selecting, alt, forwardWheel}` (`selecting` = the conversation's selection mode, which hovers and picks like comment mode), `redline:set-pins {pins}`, `redline:set-marks {marks: [{number, selector}]}` (numbered chip marks, drawn whenever there are some); artboard->parent `redline:ready` (sent on every load, re-send state then), `redline:picked {selector,xPct,yPct}`, `redline:pin-positions {positions}`, `redline:escape` (Escape pressed in selection mode: the iframe holds the keyboard focus, so the parent cannot hear it), `redline:doc-height {height}` (height of the whole page; on load, on resize and when the tweaks change, only when it changed). Extend this protocol (new `redline:*` types) rather than adding another injected script. Bridge tests run the served script in jsdom (`packages/server/test/pin-bridge.test.ts`; jsdom has no layout, stub `getBoundingClientRect`/`scrollWidth`).
- Artboard HTML responses are no longer byte-identical to the stored file (bridge tag appended before `</body>`); read stored content through `/api/pages/:id/files/*`.

## Page manifest (ticket 19)
- File `manifest.json` (`MANIFEST_PATH`) at the root of a page's files, part of every version and of the working copy. Types and `parseManifest(text)` / `defaultManifest(paths)` live in `@redline/shared`; always read it through `parseManifest` (it fills defaults and throws `Invalid manifest.json: ...`). Server routes creating a page or a version return 400 when a `manifest.json` or `tweaks.json` does not parse (same check for `/api` and `/agent-api`).
- Shape: `{ title?, designSystem? (design system id), artboards: [{ file, title?, width=800, height=500, x, y, frame? ("phone"|"tablet"|"browser"|"paper"; unknown, `"none"` or the former `device` field = refused at publish by `parseManifest`, naming `artboards[i].frame` / `artboards[i].device was renamed to frame`; no frame = shown as is; renamed from `device` 2026-10-24), url? (browser address bar text, only with `frame: "browser"`), expand? ("fill"; anything else refused at publish by `parseManifest`, naming `artboards[i].expand`), guides?: { columns (whole number > 0), gutter (>= 0), margin (>= 0), baseline? (> 0) } }], elements: [{ kind? ("title" by default), text, subtitle?, width=1200, x, y }] (ordered canvas decoration, drawn in list order, not draggable, no pins, absent from play mode; legacy `notes: [{ text, x, y }]` still reads as titles, `notes` together with `elements` is refused, an unknown `kind` is refused; `{ kind: "image", src ("assets/…" path of the project; anything else, `..` included, is refused naming `elements[i].src`), width=400, x, y }` draws the file at that width with its natural ratio and the path as caption, loaded from the artboard origin `/pages/<pageId>/<src>`; `kind: "link"` (ticket 05, 640x112 card, `LINK_CARD_WIDTH`/`LINK_CARD_HEIGHT`) takes either `page` (page id; shows the target's title, `PageThumbnail` and project, same-tab `#/pages/<id>` link, "Page introuvable" when the page is gone) or `url` (http/https) + `title` (shows the hostname, opens in a new tab); both, or neither, is refused naming `elements[i].page`/`.url`/`.title`; to add a kind, extend `ManifestElement` and `ELEMENT_PARSERS` in `@redline/shared` the switch in `packages/web/src/CanvasElements.tsx`, and `elementBox` in `packages/web/src/canvasGeometry.ts` (the box arrows target)), links: [{ from, selector, to }] (artboard files; play mode), tweaks: [{ id, type ("color"|"choice"|"toggle"|"range"|"count"|"text"), label, default?, options? (choice), min?/max? (range, count) }] }`. Positions and sizes are canvas pixels. `artboards[].file` is the artboard identity (threads reference it). Missing x defaults to the right of the previous artboard. A page has NO type (removed 2026-10-22): an old manifest that still carries `type` parses fine and the field is ignored.
- Guides (lot A ticket 07): `artboards[].guides` is a column grid in canvas pixels, validated by `parseManifest` (error names `artboards[i].guides.<field>`, so a bad value is refused at publish). The canvas draws them (`ArtboardGuides.tsx`: columns, gutter = gap, margin = side padding, optional baseline lines) over each artboard that declares them, only while the viewer toggles "Guides (G)" (button next to the zoom or G key); the choice is per viewer, kept in `localStorage` key `redline:guides`.
- Text and sticky notes (lot A ticket 02): elements `{ kind: "text", text, width=360, size="m", color?, x, y }` (colour tints the text) and `{ kind: "sticky", text, width=240, size="m", color="yellow", x, y }` (colour fills the background); sizes `s|m|l` (`NOTE_SIZES`), an unknown `color`/`size` is refused naming `elements[i].color|size`. The palette names live in `@redline/shared` (`PALETTE_COLORS`, `PaletteColor`); the shades live in `packages/web/src/canvasPalette.ts` (`paletteShades(color, theme)` -> `{ fill, stroke, text }`, light and dark sets) and are reused by shapes and arrows. The markdown subset (bold, italic, bullets, http(s) links in a new tab, the rest plain text) is `parseNoteMarkdown` in `packages/web/src/noteMarkdown.ts`; rendering is `CanvasNotes.tsx` (`[data-canvas-text]`, `[data-canvas-sticky]`). Font sizes (canvas px): s 22, m 26, l 30.
- Responsive artboards (lot A ticket 11): `artboards[].responsive` lists formats, each a name of `RESPONSIVE_FORMATS` (`desktop` 1440x900, `tablet-landscape` 1024x768, `tablet` 768x1024, `mobile` 390x844) or `{format, width, height}` (format = a format name; the override sets the viewport; the former `device` key is refused naming `.device was renamed to format`). Parsed to `ArtboardRendering[]` `{format, width, height}`; an unknown format or a non-positive size is refused naming `artboards[i].responsive[j](.device|.width|.height)`; two renderings with the same format and width are refused. `frame` is ignored on a responsive artboard, and the parsed `width`/`height` describe the frame at the declared heights. Rendering identity: `renderingKey` (`desktop-1440`) and `renderingLabel` ("Desktop · 1440") in `@redline/shared`; reuse them for threads, chips and play (tickets 12-14). Geometry: `responsiveFrameLayout(origin, renderingSlots(renderings), { measuredHeights, hidden })` -> `{ frame, renderings: [{ key, x, y, width, height }] }`: one step `RESPONSIVE_SPACING` (96) is both the frame padding and the gap; each rendering uses its measured height (else the declared one); keys in `hidden` are dropped and the frame closes up. UI: `ResponsiveFrame.tsx` (`[data-responsive-frame]`, `[data-rendering=<key>]`), under one strip (name, "responsive" badge, buttons once) in `PageCanvas`. Page heights come from the bridge (`redline:doc-height`) and are kept per file then rendering key in `PageCanvas`. Every rendering gets the full tweak values. Threads in a rendering (ticket 12): `Thread.rendering?` / `CreateThreadRequest.rendering?` = `ThreadRendering {format, width}` (column `threads.rendering`, JSON; validated at `POST /api/pages/:id/threads`: known format, positive number width, else 400 (`threadRenderingError` in `validation.ts`)). `ResponsiveFrame` passes each rendering the threads whose `renderingKey` matches, and `onPick` reports the rendering, so the draft carries it; threads without a rendering (plain artboards, older threads) show on no rendering of a responsive artboard. The comments panel shows `RenderingChip.tsx` (`[data-testid=thread-rendering]`, "Mobile · 390") on the thread header (card, failed, held). The session message says `(vu en Mobile · 390 px: ... fix that breakpoint)` after the artboard (`renderingText` in `work.ts`, single and batch messages). For the per-rendering thread count (ticket 13) filter `threads` by `renderingKey(t.rendering)`.
- Tweak grid (lot E ticket 04): `artboards[].matrix = { rows?, columns?, blocks? }`, each a tweak id (`TweakGridDeclaration` in `@redline/shared`, `tweakGrid.ts`). `parseManifest` refuses, naming `artboards[i] (<file>).matrix`: a key other than the three, an unknown tweak or one not shown on that artboard (`tweakAppliesTo`: its own `artboard`, or page-level on the first artboard), a tweak that is not `choice` or `toggle`, the same tweak twice, no dimension, more than `MAX_TWEAK_GRID_CELLS` (60) cells, `responsive` on the same artboard; so every publish path (HTTP, session, terminal) refuses it. `width`/`height` stay the size of ONE cell (play mode shows the artboard once at that size; the canvas frame is computed). `tweakGrid(matrix, tweaks)` -> `{ columns, blocks: [{ label?, rows: [{ label?, cells: [{ key, values }] }] }] }`: labels are the choice options in declared order, a toggle gives `<label> : non` then `<label> : oui`; an undeclared dimension is one unlabelled entry. `tweakGridLayout(grid, cellSize)` positions blocks titles, column headers, row labels and cells inside the frame with the board's metrics (`TWEAK_GRID_METRICS`: 1 px border, 24/20 padding, 96 px label column, 6 px gaps, 22 px between blocks). UI: `TweakGridFrame.tsx` (`[data-tweak-grid]`, `[data-grid-cell=<key>]`, `[data-grid-block|column|row]`): each cell is a `bare` `ArtboardFrame` (no clip, shadow or background) given the page tweak values overridden by the cell's combination; the strip spans the frame (`artboardBoxes` holds the frame box, so arrows and the table of contents use it) and carries a "grille · état × variante" pill. Threads in a cell (lot E ticket 05): `Thread.cell?` / `CreateElementThreadRequest.cell?` / element `ThreadTarget.cell?` = `TweakValues` of the grid's tweaks only (tweak id -> value, in rows, columns, blocks order; column `threads.cell`, JSON; validated at `POST /api/pages/:id/threads` and in chips by `threadCellError`: non-empty object of string, finite number or boolean, else 400). `cellKey(cell)` is the cell identity (sorted entries), `cellText(cell, tweaks?)` the readable form: "Hover · Outlined · Icône : non" in the UI (toggle with its label from the page tweaks, `PageTweaksContext`), "Hover · Outlined · icon off" for Claude (the server has no manifest at hand). `TweakGridFrame` gives each cell the threads whose `cell` has its key (threads from before cells, without `cell`, show in the first cell), `marksOf(cell)` for chips (`marksFor(chips, file, rendering?, cell?)`) and `onPick(pick, cell)`, which puts `cell` on the draft and chips; a cell holding pins is drawn above its neighbours (pins overflow the element edge). The comments panel shows `RenderingChip` (`[data-testid=thread-cell]`, "vu en Hover · Outlined · Icône : non") next to the rendering chip; the session message says `(vu en Hover · Outlined · icon off: ...)` after the artboard (`cellSeenText` in `thread-subject.ts`, single messages; chip lines in conversations without the explanation). Play mode ignores `matrix`: the artboard once at the cell size, with its Tweaks panel (all tweaks, the dimension ones included).
- View settings and hidden renderings (lot A ticket 13): per-page, server-side viewer state `PageViewSettings { hiddenFormats: ResponsiveFormat[], renderingOverrides[artboard file][renderingKey] = shown }` (`@redline/shared`; `EMPTY_VIEW_SETTINGS`). Table `page_view_settings` (created in the `Store` constructor; `getViewSettings` / `setViewSettings`), read with the page (`GET /api/pages/:pageId` adds `viewSettings`; `Page.viewSettings` is optional and only set there), written with `POST /api/pages/:pageId/view-settings` (full object, validated by `viewSettingsError` in `validation.ts`, 400/404). Not a version, not in the working copy, no queue entry: never put view state in the manifest or send it to sessions. Web logic in `viewSettings.ts` (`hiddenRenderingKeys` = effective hidden set, a frame's override wins over its format, the first rendering stays if all would be hidden; `toggleRendering` refuses to hide the last shown one; `setFormatShown` applies to every frame and clears that format's overrides) feeds `responsiveFrameLayout({ hidden })`, so arrows and the frame close up. UI: `RenderingControls.tsx` (`RenderingChips` in the strip, `RenderingsMenu` "Rendus" in the bottom bar, only when the page has a responsive artboard). A hidden rendering's chip counts its threads (`threads.filter` by `renderingKey`, "Mobile · 1 fil masqué"). Threads without `rendering` on a responsive artboard (older ones) show in the frame's first shown rendering, so they are never hidden. The responsive strip sits 8 px above its frame (board `CanvasResponsive`).
- Element ids and arrows (lot A ticket 04): every non-arrow element takes an optional `id` (`parseElement`); `checkElementIds` in `parseManifest` refuses a duplicate id (also against artboard files) and an arrow naming an unknown id (`elements[i].to names "x", ...`). Arrow: `{ kind: "arrow", from, to, label?, color="gray", line="solid"|"dashed" }`, `ArrowEnd = id | {x, y}`. Pure geometry is `packages/web/src/canvasGeometry.ts` (`arrowGeometry(from, to)` -> `{ start, end, path, label }` on the middles of the two closest edges: a straight line when both ends share a row or a column, else a soft cubic curve leaving and entering perpendicular to the edges (label at the curve's middle; nothing to declare in the manifest); `elementBox(element, measured)`; `responsiveFrameLayout`/`responsiveFrameBox` for responsive frames, see below). `CanvasElements` measures id'd elements from the DOM (`offsetWidth/Height`, ResizeObserver; link cards use `LINK_CARD_WIDTH/HEIGHT`) and takes `artboardBoxes` (artboard file -> box; a responsive artboard's box is its whole frame); arrows are `svg[data-canvas-arrow] > path` plus `[data-canvas-arrow-label]` (stroke 3.2, dash 12 10, label 22px: the board's values doubled).
- Shapes (lot A ticket 03): `{ kind: "shape", shape: "rect"|"ellipse", style="outline"|"fill", color="gray", label?, width, height, x, y }` (width/height required and positive; an unknown `shape`/`style`/`color` is refused naming `elements[i].<field>`). `outline` = 4px stroke in the palette `stroke` shade, `fill` = that stroke colour at 15 % (`color-mix`), the label (26px, semibold, stroke colour) sits top-left inside a rect and centred in an ellipse. Rendering is `CanvasShapes.tsx` (`[data-canvas-shape]`, `pointer-events: none`); shapes are drawn under the artboards, every other element (arrows included) above them in list order: `PageCanvas` renders the artboards as `CanvasElements`' children, which sit between the shapes and the rest.
- No manifest: every `.html` file is laid out side by side at 800x500 (`defaultManifest`). Tweak values never go in the manifest (tweaks file, ticket 22).
- Web: `PageCanvas` takes `files` (version path->hash map), loads the manifest per version and renders artboards in a zoom/pan viewport (`canvasView.ts`: `zoomAt`, `panBy`, `fitView`; wheel pans, ctrl/cmd+wheel zooms, drag pans). `ArtboardFrame` takes `width`/`height`/`zoom`; pins are `[data-pin=<number>]`. The web vite config aliases `@redline/shared` to source.
- Folder link (ticket 05): `.redline/project.json` `{projectId}` written by `linkFolder` (`packages/agent/src/link.ts`, also adds `.redline/` to `.gitignore`); project agents send `projectId` in the hello, server refuses a second online one (close 4409 `project_taken`); `GET /api/projects` returns `agent` per project; CLI `redline init`.
- Play frames (lot A ticket 08): `presentationOf(artboard, framed=true)` (`playFrames.ts`) gives `{frame, viewport, frameHeight, stagePadding}` (`frame` is an `ArtboardFrame` or `"none"`): declared `frame`, else `none` (no inference from the size, decided 2026-10-24); a phone plays in a fixed 390x760 viewport, others in the artboard size; `framed=false` forces `none` (the "Habillage" switch is ticket 09; `PlayMode` has `framed = true` for now). `PlayFrame.tsx` draws the shell at natural size (phone: camera pill + home indicator over the iframe; tablet: camera dot + 22px home strip; browser: 36px bar with the `url`, empty when absent; paper: sheet + shadow, stage turns grey via `main[data-frame=paper]`); `PlayMode` scales only the iframe to fit the stage (the frame keeps its real size; browser stage padding 44, paper 14, others 32). Stage and shell carry `data-frame`.
- Habillage (lot A ticket 09): `presentationOf(artboard, framed, windowWidth)` also returns `fill` ("none" | "height" | "both"), `framable` (declared frame is not `none` and the window is not narrow: the "Habillage" button shows only then) and `mobileBar`. Frame off: phone/tablet keep their width at stage height (`height`), browser fills (`both`); window under 600 px (phone) or 1100 px (tablet): no frame, `both`, and for a phone a 44 px bar (back + "page · file") replaces the top bar and the tweaks panel. The choice is per viewer in `localStorage` `redline:play-framed` (`useStoredToggle`, default on; paper is never framable, so it keeps its sheet whatever the switch says). `main` carries `data-fill` when stretched.
- Fluid artboards (lot A ticket 10): `expand: "fill"` makes `presentationOf` return `fill: true` (frame `none`, no frame, stage padding 0) unless the declared frame is `phone`; `PlayMode` then renders the iframe at the stage size, scale 1 (`main[data-fill]`). The canvas keeps the declared size. Guides in play: the same per-viewer `useStoredToggle("redline:guides")` state, owned by `PageCanvas` and passed to `PlayMode` (`guidesVisible`, `onToggleGuides`; the canvas G handler is off while playing); the shared `GuidesButton` in the header only while the current artboard declares guides, and the G key (ignored in fields, `isEditableTarget`); `ArtboardGuides` is drawn over the scaled viewport. The session guide (`agent/src/guide.ts`) documents `"expand": "fill"`.
- Responsive artboards in play (lot A ticket 14): `presentationOf(artboard, framed, windowWidth, rendering?)`: with a rendering `{format, width, height}` the presentation is the frame of its format (desktop -> browser window, tablet / tablet-landscape -> tablet, mobile -> phone) at exactly the rendering's width and height (the page scrolls inside the iframe), with the same "Habillage" and narrow-window rules; the mobile rendering in a window under 600 px gets the 44 px bar, which then holds a compact `select` "Rendu responsive" instead of the button group; `null` = "Aucun": no frame, `fill: "both"`, no "Habillage" button; `undefined` = not responsive. `PlayMode` shows a `role=group` "Rendu responsive" segmented selector next to the title (one button per rendering with its format label, `renderingLabel` when a format repeats, then "Aucun"). The choice is per viewer in `localStorage` `redline:play-rendering` (`usePlayRendering.ts`: a `renderingKey` or `none`; a key the artboard does not declare falls back to its first rendering). `expand` and `frame` are ignored on a responsive artboard.
- Play header (lot A fix pass): the nav lists each artboard by `title` (else "Artboard N"); the page title (not `manifest.title`) names the header and the mobile bar; "Tweaks" is a toggle button shown only when the manifest has tweaks (panel open by default, `useStoredToggle("redline:play-tweaks", true)`); "Guides (G)" and "Habillage" appear only when they apply.
- Play mode (ticket 21): `PlayMode.tsx` swaps in for the canvas; bridge message `redline:set-links {selectors|null}` (parent->artboard) makes clicks on matching elements (or descendants) report `redline:link {selector}` instead of acting; target comes from `manifest.links` (`resolveLink`).

## Design systems (ticket 26)
- A design system is a project (same id) with any number of ordinary pages (`POST /api/projects/:id/pages` works on it; `DesignSystem {id,title,pageId}`, `pageId` = its first page, table `design_systems`); `GET/POST /api/design-systems` (POST `{title, files}`), design systems are not listed by `GET /api/projects`. ## Tweaks (ticket 22)
- Declarations: `manifest.tweaks` (see Page manifest). Values: file `tweaks.json` (`TWEAKS_PATH`) at the root of the page's files, a flat JSON object `{ "<tweakId>": <string|number|boolean> }`, e.g. `{"accent":"#0f766e","search":false,"gap":12}`. ## Page lock and queue (ticket 11): THE dispatch path
- Every work item (thread now; reply 10, batch 12, conversation 16/17, retry, terminal mode 24...) goes through `PageLock` (`packages/server/src/page-lock.ts`, one instance per main app, built in `buildMainApp`). Never call `hub.send(agentId, {type:"work"})` directly.
- API: `pageLock.submit({projectId, agentId?, takeoverItem?}, item: WorkItem)` queues the item (built with its own `randomUUID()` id and `item.pageId`); `agentId` pins it to one agent (resumed sessions). There is no `onDispatched` callback any more: when it sends an item the lock itself records the session (`setThreadSession` for each `item.threads`, `setConversationSession` for `item.conversationId`, clears a ready "Nouvelle session" seed on a non-resume item) and emits `work-dispatched`, so everything an item needs on dispatch must be derivable from the item (that is also what makes it persistable). It is sent to the project's online agent (or the pinned one) once (a) no other item is active on that page and (b) an agent is online, otherwise it waits (FIFO per page; different pages run in parallel; an item that no agent can run yet does not hold back other items of its page, except items of its own session, which never overtake it). `pageLock.release(workId)` frees the page; it is called automatically on `work-done` / `work-failed` (observed on `store.onChange`), call it yourself only for items that never reach an agent (e.g. a server-side/terminal lock holder). `pageLock.waiting(pageId): QueueEntry[]`.
- Agent drops while running an item: the item returns to the front of the queue (nothing was published) and re-runs when an agent is online; ticket 16's retry/backoff should hook there (`requeueActiveOf`).
- `dispatchThread(store, pageLock, projectId, thread)` and `dispatchReply(store, pageLock, projectId, thread, body)` in `work.ts` build a thread item and submit it; follow that shape for new kinds.
- Hub: `AgentHub.onAgentOnline(listener)` / `onAgentOffline(listener)` (after welcome / on socket end).
- Web: `GET /api/pages/:id/queue` -> `QueueEntry {workId,pageId,threadIds,reason:"page-busy"|"agent-offline"}`; SSE `queue-updated {pageId}` after every change; `queueLabel(queue, threadId)` (`packages/web/src/queueLabel.ts`) gives "En file · <reason>" (rendered with `data-testid="queued"` in the thread list). Items not tied to threads have empty `threadIds`; surface them in their own UI.
- Persistence: the lock mirrors its state in table `work_queue` (`store.saveWorkQueue/loadWorkQueue`, one row per item: state `active`/`queued`/`retrying`/`failed`, pin, item, takeover item, attempts, retry time and message) after every change, and `pageLock.restore()` (called by `buildMainApp` once every store listener exists) brings it back: the item that was running goes back to the HEAD of its page queue, retries are re-scheduled for their remaining time, failed-for-good items stay "Relancer"-able, and `work-dispatched` + `work-retrying` / `work-failed` events are replayed so the run tracker shows them. Server-side holders (`acquire`) are not persisted. `pageLock.itemOf(workId)` finds an item wherever it is (queue, running, retrying, failed): use it instead of per-work maps in memory (`WorkItem.conversationId`, `WorkItem.summaryForThread` carry what the trackers need). Run live state (steps, streamed text, answered runs) is NOT persisted.
- Agents may only report (`work-event/done/failed`) on the work item the lock sent to them (`AgentHub.acceptWorkMessagesFrom`); other reports are ignored.
- Tests: `packages/server/test/page-lock.test.ts` and `queue-robustness.test.ts` drive it with a raw `server.connectAgent` and `agent.send({type:"work-done", workId})`; `queue-robustness` also covers restart (`server.restart()`), takeover and retries.
- The sent item keeps the queued item's id even when a takeover item is sent (the lock and the agent's reports are keyed by it).

## Retries and failure (ticket 12)
- `PageLock` (not the agent) retries: on `work-failed` the item leaves the page (next item may run) and is re-queued at the FRONT after a delay: subscription limit (`isSubscriptionLimit`, reset from `limitResetAt` in `retry-policy.ts`: epoch `limit reached|<s>` or `resets 3pm`; unknown = 15 min; not counted as an attempt) else 1, 5, 15 min (`RETRY_DELAYS_MS`; override with `retryDelaysMs` in `startTestServer`/`startSeam2`/`buildMainApp` options; `[]` = fail at once). Server event `work-retrying {pageId,workId,threadIds,retryAt,limit,message}`; run status `retrying` (`retryAt`, `limit`).
- Past the ladder the item is kept as failed (memory): `POST /api/pages/:pageId/runs/:workId/retry` (`retryRunPath`, 204/404) = `pageLock.retry(workId)` re-queues the same item (same model/effort/session). Web `RunProgress` shows "Échec", "Rien n'a été publié." and "Relancer".
- The limit text patterns are guesses (no recorded fixture of a real limit); they are isolated at the top of `retry-policy.ts` and documented as unverified in `docs/claude-code-engine.md`; adjust them when one is captured.
- A retried (or requeued after an agent drop) item with `resume: false` starts under a NEW session id (`withFreshSession`), because the failed attempt may have created the session and `--session-id` of an existing session is refused; the lock records the new id when it is sent. A resumed item keeps its session. A reply sent while an item waits for its retry joins that item (`amendQueued` also searches items waiting for a retry).

## Global agent and takeover (ticket 17)
- Agent choice lives in `PageLock.pickTarget` + `chooseAgent(store, projectId)` (`agent-selection.ts`): project agent online; else global agent when the project never had a project agent; else (project agent offline) global agent only if the project's EFFECTIVE takeover is on (`Project.globalTakeover` = `globalTakeoverOverride ?? global setting`, see the 2026-10-22 section); otherwise the item waits (`agent-offline`). ## Final review fixes (integration branch)
- Publishing (`mergeOntoCurrent`, `publish.ts`): an agent publish (`POST /agent-api/pages/:id/versions`) sends the whole working copy AND `baseVersionId` (the `AgentCheckout.versionId` it was checked out from; 400 without it). The server applies only what the session changed relative to that base on top of the page's CURRENT version (per file: untouched by the session -> keep current; changed/deleted by the session -> apply when the current file still equals the base or the same change; otherwise 409 `conflicting files: ...`, nothing published). So a tweak, a restore or another session's version made meanwhile is never reverted. The answer carries `merged: true` when the page had moved on. A conflicting run fails and follows the retry ladder (it re-checks out). Terminal mode (`publish_page`) re-downloads the page after a merged publish so its base stays truthful; it still waits for the page lock. The merged result is validated like any version.
- `/api` hardening (`request-hardening.ts`): non-GET `/api/*` requests are refused (403) when they carry an `Origin` whose host differs from `X-Forwarded-Host`/`Host`, and (415) when they have a body that is not `application/json` (the raw asset PUT is only origin-checked). `X-Frame-Options: SAMEORIGIN` + CSP `frame-ancestors 'self'` on every response of the main app; `GET /api/pages/:id/files/*` is `nosniff` + `Content-Disposition: attachment`. Asset uploads accept 20 MB (`MAX_ASSET_BYTES`), everything else Fastify's 1 MB. Compare secrets with `tokensEqual`. The proxy must forward `Host` or `X-Forwarded-Host`.
- Docker publishes the ports on `127.0.0.1` (`REDLINE_BIND` to change).
- Design system live reload: `design-system-updated {designSystemId, pageIds}` (`design-system-reload.ts`) when a design system's page gets a version; `PageCanvas` remounts its artboards when its page is listed.
- Agent: `serveAgent` (`serve-agent.ts`) = connect + reconnect with backoff (1, 2, 5, 10, 30 s) while the server is unreachable or the connection is lost; a refusal by the server (wrong token, incompatible protocol, unknown project, project taken) or a regenerated token ends it (`done` rejects). `redline init`/`agent` list and create projects through `/agent-api/projects` (`linkFolder({..., token})`). `login.json` is forced to 0600. Session permissions: reads limited to the agent's folder (see `docs/claude-code-engine.md`).

## Product decisions of 2026-10-22 (server, shared, agent)
Contracts for the UI. Types are in `@redline/shared`.

- **No page type.** `Page` = `{id, projectId, title, createdBy: "claude"|"user", version}`. `CreatePageRequest` = `{title, files}` (an extra `type` is ignored). `PAGE_TYPES`/`PageType` are gone. SQLite: the `pages.type` column is dropped at startup when present.
- **Global takeover (decision 6).** `GET /api/settings` -> `Settings {globalTakeover: boolean}` (default false); `PATCH /api/settings {globalTakeover}` (400 non-boolean). `Project.globalTakeoverOverride: boolean|null` (null = follow the global setting) and `Project.globalTakeover` (effective, `override ?? global`, what dispatch uses). `PATCH /api/projects/:id {globalTakeoverOverride: true|false|null}`. Both PATCHes re-pump the queue. The old boolean `allowGlobalTakeover` is gone; a stored `1` becomes an override of `true`. `HomeOverview` covered projects carry `globalTakeover` (effective).
- **Rename (8g).** `PATCH /api/projects/:id {title}` (same route as above, fields are independent) and `PATCH /api/pages/:pageId {title}` -> the entity. Title trimmed, non-empty, at most `MAX_TITLE_LENGTH` (120) characters, else 400. Creation has no uniqueness rule, so renaming has none either.
- **Page creator and created pages (8d).** `Page.createdBy`; existing pages are "user". `create_page` creates with "claude" and records the page against the run (`workId` sent by the agent; table `run_created_pages`). The FIRST Claude answer of that run carries them: `ThreadReply.createdPages` / `ConversationMessage.createdPages` = `CreatedPage[] {pageId, name, artboardCount}` (name and count are read live). Agent-api bodies: `AgentReplyRequest {body, workId?}`, `CreateSiblingRequest {title, workId?}`.
- **Conversations (8e).** `Conversation` (list and detail) has `exchangeCount` (number of user messages: a user message plus Claude's answer is one exchange; an unanswered one counts) and `lastActivityAt` (latest message, else `createdAt`).
- **Element name (8f).** `Thread.elementName: string|null`; `CreateThreadRequest.elementName?` (string, at most `MAX_ELEMENT_NAME_LENGTH` 200). Also `WorkThread.elementName?`; the session message adds "(named « name »)" after the element selector. The bridge computes the name (UI side); the selector stays the exact reference.
- **Version origin.** `PageVersionSummary.originId?/originLabel?` (thread = first thread of a batch, or conversation; title snapshot). Set when an agent publishes with `workId` (`CreateVersionRequest.workId`, `/agent-api` only; the item must belong to that page). Old versions and other origins have none: the UI falls back to the origin kind.
- **Per-artboard history (decision 3).** An "artboard version" is a page version in which the content of that file changed; tweak versions are skipped. Nothing new is stored beyond the version origin columns.
  - `GET /api/pages/:pageId/artboard-versions?file=<artboard file>` -> `ArtboardVersion[]` newest first: `{versionId, title, origin, originId?, originLabel?, createdAt, current}`. `title` is the version message, except origin `creation` which reads "Artboard créé". Restores/put-backs carry the fixed messages "Version du <date> restaurée" and "Remis depuis les artboards supprimés". `current` is true for the one entry the page shows (none when the artboard is deleted). Unknown file: `[]`.
  - Preview: `GET <artboardOrigin>/page-versions/:pageId/:versionId/<path>` (`versionPreviewPath(pageId, versionId, file)`): any file of the page as in that version, same sandbox CSP, bridge and design system injections as live artboards, project assets fall back as usual. Use it for the read-only preview iframe and for thumbnails (pins hidden by the UI).
  - `POST /api/pages/:pageId/artboards/restore {file, versionId, timeZone?}` -> 201 `{version: PageVersionSummary, previousVersionId}`. Puts ONE artboard back to its state in page version `versionId`: new page version, origin `restore`, only that file changes (its manifest entry too, only when the artboard is not on the page now: re-added with the position/size it had in `versionId`'s manifest). Message: "Version du <date, fr-FR, in timeZone> restaurée" (the date is `versionId`'s); "Remis depuis les artboards supprimés" when the artboard was not on the page; "Remise annulée" when the file does not exist in `versionId`. 409 when it already is in that state; 404 unknown page/version; 400 bad file/versionId/timeZone.
  - **Undo** = the same call with `versionId = previousVersionId` (the entry that was current before, or the page head when the artboard was absent, which removes it again). So "Annuler" after "Restaurer" or "Remettre" is `POST .../artboards/restore {file, versionId: previousVersionId}`.
  - `GET /api/pages/:pageId/deleted-artboards` -> `DeletedArtboard[]` newest first, only artboards absent now: `{file, title?, deletedBy: "claude"|"user", origin, originId?, originLabel?, deletedAt, lastVersionId, width, height}`. "On the page" = listed in the manifest with its file present (every `.html` when there is no manifest). `deletedBy` is "claude" for thread, conversation and terminal versions, "user" for restore (an undone put-back). There is no inline content: use `lastVersionId` with the preview path for the thumbnail. Put back = the restore call with `versionId = lastVersionId`.
  - The older whole-page `POST /api/pages/:pageId/versions/:versionId/restore` still exists; the UI does not use it.
- **DESIGN.md written by sessions (8a).** The agent reads DESIGN.md back from the working copy (a deleted file counts as unchanged) and, if it differs from the checkout, sends `CreateVersionRequest.designMd {content, base}` with the publish (`base` = text it started from). The server answers 409 (nothing published) when the stored DESIGN.md no longer equals `base`; otherwise it saves it as a DESIGN.md version with the author derived from `workId`: `{origin: "thread"|"conversation", originId, originLabel}`, `{origin: "terminal"}` for a terminal publish (`publish_page` sends a changed DESIGN.md the same way), else `{origin: "user"}` (editor saves, `PUT /api/projects/:id/design-md`, and versions from before this field). If only DESIGN.md changed, the page still gets a version (same files).
  - `GET /api/projects/:id/design-md/versions` -> `DesignMdVersion[]` (newest first) now with `origin/originId?/originLabel?`.
  - `GET /api/projects/:id/design-md/info` -> `DesignMdInfo {versionCount, lastModified: {versionId, createdAt, origin, originId?, originLabel?} | null, rules: DesignMdRule[]}`. A **rule** is any non-blank line of DESIGN.md (list item, heading, paragraph line), compared trimmed; `line` is 1-based in the current text; each rule carries the author and `versionId`/`createdAt` of the version that introduced it: the oldest version since which a line with that text has been present in every version up to the current one (editing a line makes a new rule; for repeated texts the k-th occurrence is matched to the k-th occurrence in older versions). ## Design system tokens and pages (lot E, ticket 06)
- `tokens.css` of a design system is a project-level file of the design system's project (table `project_files`, path `tokens.css`), versioned like DESIGN.md: `design_md_versions` has a `path` column (default `DESIGN.md`), `store.saveDesignMd(projectId, path, content, author)` / `listDesignMdVersions(projectId, path?)` serve both. It is never a page file. `GET /api/design-systems/:id/tokens` and `/tokens/versions`.
- Publishing a `tokens.css` among the files of any page of a design system (`store.addVersion`, so `/api` and `/agent-api` alike) saves it as the design system's tokens (author from the version origin) and strips it from the page files; core tokens are still enforced (`tokensError`, 400 / 409). `createDesignSystem` does the same with its `files`. Working copies of design system pages do not contain `tokens.css`; `projectContext(...).designSystem.files` still does (page files plus tokens).
- Migration (`moveDesignSystemTokensToProjects`, runs at every store start, idempotent): a design system page still holding `tokens.css` gets it moved to the project level (first tokens version) and a page version without it ("Tokens moved to the design system").
- `parseTokens(css)` (`@redline/shared`, `tokens.ts`) -> `TokenDeclaration[] {name, value, isColor, deprecatedFor?}` in order (a repeated name keeps its first position and last value); `deprecatedFor` comes from `/* deprecated: renamed to --new */` after the declaration; `isColorValue` detects hex, colour functions and a few named colours.

## Moving an artboard (lot E, ticket 03)
- `store.moveArtboard(sourceId, file, {pageId} | {newPageTitle}, origin, ref?)` is the one transaction (better-sqlite3 `db.transaction`): file and manifest entry leave the source and join the target (raw manifest JSON, so unknown fields survive; placed at `max(x + width) + ARTBOARD_GAP`, `y` of the target's top artboard, same size), the artboard's threads (any status) get the next numbers of the target page, one version on each page ("<file> déplacé vers <page>", "<file> reçu de <page>"). A new page is created inside the same transaction. Nothing else moves: links, tweak declarations and view settings stay behind.
- `move-artboard.ts` (`moveArtboard(store, pageLock, ...)`) validates and answers `{status, body}`: 404 unknown page/artboard/target, 400 same page, other project, bad title, 409 target already has the file or a page is held by another work item (`PageLock.isHeldByOther(pageId, exceptWorkId)`: refused, never waited for). Routes: `POST /api/pages/:pageId/move-artboard` (origin `restore`) and `POST /agent-api/pages/:pageId/move-artboard` (`workId` lets the run pass its own page lock; origin = thread/conversation of the run, else `terminal`). Types `MoveArtboardRequest`/`MoveArtboardResponse` in shared.
- Agent: `move_artboard {file, pageId | newPageTitle}` in `createRedlineMcpServer` (sessions and terminal mode). It drops the file and manifest entry from the working copy, then `context.afterArtboardMoved`: the run re-checks the page out as its new base (so the run's own publish neither conflicts nor brings the artboard back), terminal mode refreshes its checkout. The answer carries the target page id.
- Web: `ArtboardMoreMenu` owns the "Déplacer vers" section (fetches the project's pages when opened; the design system sentence of the board only on a design system's pages), the "Nouvelle page…" dialog and the refusal dialog; dialogs render in a portal because the canvas is transformed.

## Project style (lot E, ticket 08)
- A project's style is its project-level `tokens.css` (`PROJECT_STYLE_PATH`, same storage and versioning as a design system's tokens: `project_files` + `design_md_versions` with `path = 'tokens.css'`, author = origin user / thread / conversation / terminal). A design system's own project has none (its `tokens.css` is the design system's): `store.isDesignSystemProject`.
- `store.createProject` gives a project without a design system the neutral values (`NEUTRAL_TOKENS_CSS`); with a design system it starts empty (no file). `giveProjectsTheirStyle` migrates existing projects without a design system at every store start (idempotent). `createDesignSystem` uses the private `insertProject`, so design systems get no project style.
- Artboards: `injectDesignSystem(html, designSystemId, projectId?)` links the design system's tokens, then `/project-styles/<projectId>/tokens.css` (artboard origin, `no-cache`, empty when the file is absent, 404 for a design system's project), so a project value wins by CSS order.
- `/api`: `GET|PUT /api/projects/:id/project-style` and `GET .../project-style/versions` (404 for a design system's project).
- Sessions: `ProjectContext.projectStyle?` (absent for a design system's project) is written to `tokens.css` at the root of the working copy and edited like DESIGN.md. `readWorkingCopy(dir, hasProjectStyle)` leaves the root `tokens.css` out of the page files when the checkout has a project style (in a design system's working copy `tokens.css` stays a page file, routed to the design system). `CreateVersionRequest.projectStyle {content, base}` is published with the page; a `base` that differs from the stored style gives 409 and nothing is published. The test `FakeEngine` reads `filesAtStart` with `hasProjectStyle = true`.

## Components (lot E, ticket 07)
- A component is any `components/<name>.html` (`[a-z0-9-]`) of a page of a design system or of a project (`componentNameOf(file)`, `@redline/shared`, `components.ts`). `assembleComponents(pages: ComponentPage[])` (pure; pages given in order, `{id, title, files}`) returns `{css, components, indexes, duplicates}`: `css` = the `<style data-component>` blocks in page then reading order (`readingOrder`; files absent from the manifest come last, by name), `components` = `ComponentInfo {name, file, page, groupTitle, description (<meta name="description">), usage (<template data-usage>), variants (the manifest tweaks whose `artboard` is the file), hash}`, `indexes` = per page id the index text for sessions (`## <group title>` sub-families), `duplicates` = one message per repeated name naming both files.
- Server (`packages/server/src/components.ts`): `projectComponents(store, projectId)` assembles a project or a design system (a design system is a project); `versionComponentsError` / `newPageComponentsError` refuse a duplicate at publish (400 on `/api` and `/agent-api` publish and on page creation, 409 when it only appears once merged onto the current version). The scope of a name is the project (design system) of the page.
- Serving: artboard origin `GET /design-systems/<id>/components.css` and `GET /projects/<id>/components.css` (live, `no-cache`, empty when there is no component). `injectDesignSystem(html, designSystemId, projectId?)` (`bridge.ts`) links, in `<head>` order: DS `tokens.css`, DS `components.css`, project style `tokens.css`, project `components.css` (the last two only when the page has a project style, i.e. not on a design system's own project). The artboard serving described here is the draft; project pages use diffusion files instead (see "Diffusions").
- Canvas: the strip of a component artboard shows `ComponentMarker` (◆, role img "Composant") and the component name in mono instead of the artboard title; other artboards keep their title and no marker.

## Diffusions (lot E, ticket 09): THE model tickets 10-19 build on
- **Draft / current diffusion / pending.** A design system's *draft* is its live files: project-level `tokens.css` and DESIGN.md plus the components of its pages. Its *current diffusion* is the immutable snapshot projects use. *Pending* = the draft differs from the current diffusion (`DiffusionDiff.count > 0`). Editing a design system (any path: publish, DESIGN.md, tokens) changes the draft only.
- Storage: table `design_system_diffusions` (`design_system_id`, `number` per design system, never reused, `created_at`, `origin` `user | migration`, `summary`, blob hashes of `tokens.css`, `components.css`, DESIGN.md, the component list JSON (`ComponentInfo[]`) and the per-page index JSON); `design_systems.current_diffusion` points at the current one. Rows are never updated or deleted (undo / rollback, tickets 17, add a new pointer, not a new snapshot). Store API: `designSystemDraft(id) -> {state, componentsCss, assembly}`, `createDiffusion(id, origin, summary?)` (freezes the draft, makes it current, summary defaults to `diffusionSummary(diff)`), `currentDiffusion(id)`, `listDiffusions(id)` (newest first), `readDiffusionFile(id, n, file)`, `diffusionState(id, n)`. `createDesignSystem` creates diffusion 1 ("Initial diffusion"); `giveDesignSystemsTheirFirstDiffusion` (every store start, idempotent, after the other migrations) gives diffusion 1 (origin `migration`) to design systems that have none.
- Pure diff (`@redline/shared`, `diffusion.ts`): `diffDiffusionStates(from, to: DiffusionState {tokensCss, designMd, components {name, hash}[]}) -> DiffusionDiff {tokens {changed {name, from, to}, added, removed}, components {added, changed (content hash), removed}, designMdChanged, count}` (tokens compared by parsed value, so formatting and comments are not changes); `diffusionSummary(diff)` ("1 token changed, 2 components added, DESIGN.md changed", "No change"). `DiffusionInfo`, `DesignSystemDetail` are the API types.
- API (`/api`, user only, nothing on `/agent-api` or in session tools: Claude never diffuses): `GET /api/design-systems/:id` -> `DesignSystemDetail {id, title, pageId, pages, usedBy, current, pending}`; `GET /api/design-systems/:id/diffusions` (newest first); `POST /api/design-systems/:id/diffusions` -> 201 `DiffusionInfo` (409 when nothing is pending).
- Serving (artboard origin): a project page links `/design-systems/<id>/diffusions/<n>/tokens.css` and `.../components.css` (`diffusionFileUrlPath`, immutable cache, 404 for an unknown file), then the project style and project components (still live). A design system's own pages (`store.isDesignSystemPage`) link the draft `/design-systems/<id>/tokens.css|components.css` (live) and always use their own design system, whatever their manifest names. `injectDesignSystem(html, dsId, projectId?, diffusion?)`: with a diffusion number it links that diffusion's files, else the draft. `/page-versions/...` currently uses the current diffusion (ticket 13 records and uses the diffusion of each version); a preview with the draft (ticket 12) is `injectDesignSystem` without a diffusion.
- Reload: `design-system-updated {designSystemId, pageIds}` is emitted for the design system's own pages when one of them gets a version (`registerDesignSystemReload`) and for the pages of the projects that follow it when a diffusion is created (`announceDiffusion`). Still nothing reloads open pages when a project's style or components change.
